## 1. 前七章的主线：每一章都在补一块"能力"

| 章节 | 核心问题 | 关键概念 | 在 HaloAgent 中的落点 |
|---|---|---|---|
| 第 1 章 | 智能体是什么？ | LLM + 工具 + 记忆 + 规划；Agent Loop；终止条件 | `BaseAgent.run()`、`AgentOutcome`、工具/记忆/步数上限 |
| 第 2 章 | 智能体从哪里来？ | 符号主义 → 强化学习 → LLM Agent | 设计取舍：不重复造"大而全"，保留可解释性 |
| 第 3 章 | 大脑怎么工作？ | Transformer、token、上下文窗口、幻觉、采样参数 | `ChatModel`、token 估算、ContextBuilder、工具事实校验 |
| 第 4 章 | 怎么让大脑会思考会行动？ | ReAct / Plan-and-Solve / Reflection | 三个范式类，共享同一套运行时 |

| 第 6 章 | 主流框架怎么用？ | LangChain / AutoGen / AgentScope 等 | 反面教材：过度抽象、黑盒、依赖重；正面：工具生态 |

- 第 1 章的 Agent Loop 是 `BaseAgent.run()` 的雏形；
- 第 3 章的 token/上下文限制，直接变成 Memory 的预算裁剪；
- 第 4 章的三个范式，在框架里只允许重写 `_execute()`；
- 第 5 章的节点编排，抽象成 YAML 的 `tool / agent / template / condition / output`；
- 第 6 章的框架痛点，反过来成为"为什么只保留 7 个模块"的设计依据。

## 2. 第 7 章的关键判断：框架到底该"薄"到什么程度

教材总结了主流框架的四个痛点：**过度抽象的复杂性、快速迭代的不稳定性、黑盒化的实现逻辑、依赖关系的复杂性**。
本周最大的收获，不是"写出了多少功能"，而是学会了做减法。

HaloAgent 最后只保留 7 个概念：

```text
接入层     CLI / Python API / YAML Workflow
范式层     Simple / ReAct / Plan-and-Solve / Reflection
运行时     BaseAgent + Memory/Context + ToolRegistry + Tracer
适配层     ChatModel -> OpenAICompat / Mock / Retrying
```

### 2.1 只有 `BaseAgent` 是"特殊"的

很多框架会为 Memory、RAG、MCP 各造一套抽象。HaloAgent 的选择是：

- **Agent 是唯一的核心类**；
- 工具、记忆、检索、协议，尽量收敛成"Agent 可以调用的能力"；
- 范式只决定"怎么组织思考"，不重复实现工具调用、日志、异常。

这带来一个很实际的好处：三范式对比时，差异只来自**思考路径**，而不是"三套代码各自实现了一遍工具调用"。
如果每个范式都自己写一遍 `try/except`、token 统计、日志，那么对比就失真了。

### 2.2 `run()` 是公开接口，`_execute()` 是扩展点

教材第 7 章明确把 `run` 和 `_execute` 分开。本周照做了，并且把"生命周期"全部放进 `run()`：

```text
run(task):
  创建 run_id / Tracer
  memory.add(user task)
  outcome = self._execute(task)     # 子类只写这里
  兜底异常 -> status
  memory.add(final answer)
  写 trace.jsonl + result.json
  返回 RunResult
```

这样新增一个范式只需要：

```python
class MyAgent(BaseAgent):
    paradigm = "my"
    def _execute(self, task: str) -> AgentOutcome:
        ...
```

不需要关心重试、token、Trace、上下文预算。这是"框架"和"脚本"最本质的区别。

### 2.3 模型层：用标准协议换兼容性

第 7 章选择 OpenAI 标准 API，而不是为每家写 SDK。本周也采用这一判断：

- `OpenAICompatModel` 只依赖 `/v1/chat/completions`；
- `router.py` 用 provider 预设解决"环境变量名、默认 base_url、默认模型"的差异；
- `RetryingChatModel` 独立于供应商，只认 `LLMError.retryable`；
- `MockChatModel` 让单测和演示不依赖网络。

一个细节：OpenAI SDK 自带重试，会让我们在 Trace 里看到的"重试次数"失真。
所以创建 client 时显式 `max_retries=0`，把重试权收归框架。这是"可观测性"对实现的一个具体影响。

## 3. 工程实现：几个值得记录的设计

### 3.1 工具 Schema：从函数签名自动生成

第 4 章说工具三要素是"名称 / 描述 / 执行逻辑"，第 7 章进一步要求参数定义。
本周用 `inspect.signature` + `typing.get_type_hints` + docstring 自动生成 JSON Schema。

踩过一个坑：Python 的 `from __future__ import annotations` 会把注解变成字符串，
如果直接读 `parameter.annotation`，`int` 会被当成 `string`，工具参数永远不转类型。
解决方案是先用 `typing.get_type_hints(func)` 解析，再退回原始注解。

另一个细节：模型经常把 `"3"` 传给 `int` 参数。`ToolSpec.validate()` 做了**受控转换**：
- `"41"` -> `41`；
- `"abc"` -> 明确的校验错误；
- 未知参数 -> 报错并列出可用参数，让模型能自我修正。

### 3.2 工具错误不是异常，是 Observation

ReAct 的精髓是"用观察修正判断"。如果工具一报错就抛异常，Agent 就失去了纠错机会。
所以 `ToolRegistry.try_execute()` 永远返回 `ToolResult`：

```python
result = registry.try_execute("weather", {"city": "北京"})
# ok=False, output="工具不存在：weather；可用：calculator"
```

Agent 把 `ERROR: ...` 写进 Observation，下一步模型可以换工具或改参数。
这比"捕获异常后直接失败"更符合 Agent 的工作方式，也让 Trace 里能看到"失败 -> 修正"的完整链路。

### 3.3 Context 预算：永远保留最后一条用户消息

第 3 章讲上下文窗口，第 7 章把它落到 Memory。`ContextBuilder` 的策略很朴素：

1. 系统提示固定在最前；
2. 从最新往旧保留，超出预算就丢最旧的；
3. **最后一条消息无条件保留**（通常是当前任务或最新 Observation）。

每次构建都发 `context` 事件：

```json
{"original": 9, "kept": 6, "dropped": 3, "estimated_tokens": 2410, "budget": 2600}
```

这样"为什么模型忘了前面的事"不再靠猜，而是有数字。

### 3.4 Trace：把"黑盒"拆成可回放的事件

Trace 不是普通日志，而是结构化事件：

```text
run_start -> context -> llm_request -> llm_response
          -> thought -> action -> tool_result -> observation
          -> final -> run_end
```

每个事件都有 `seq / ts / elapsed_ms / run_id / agent / type / data`。
`llm_request.data.messages` 保留当时发给模型的完整消息，`tool_result.data.output` 保留工具原始输出。
对比报告就是直接读 JSONL 生成的，不需要再解析自然语言日志。

默认脱敏 `api_key / authorization / token` 等字段；这是"可观测"和"安全"的折中。

### 3.5 低代码工作流：把画布语义收敛成 YAML

第 5 章的低代码平台有节点、连线、变量、条件。本周用 5 种节点复刻最小语义：

```yaml
- id: weather
  type: tool
  tool: weather
  args: { city: ${inputs.city} }
- id: rainy
  type: condition
  if: contains(${nodes.weather.output}, '雨')
- id: umbrella
  type: template
  when: ${nodes.rainy.output}
  template: 提醒：${inputs.city}有雨，记得带伞。
```

执行器负责拓扑排序、环检测、变量替换、条件跳过、Agent/工具调度、节点级 Trace。
它证明了一件事：**低代码平台的"魔法"并不神秘**，底层就是 DAG + 模板 + 调度 + 可观测性。

### 3.6 Reflection：评分阈值是"刹车"

第 4 章的 Reflection 是"执行 -> 反思 -> 优化"。如果只写循环，很容易无限改稿。
本周加了两个刹车：

- `reflect_rounds`：最多几轮；
- `quality_threshold`：评分 >= 8 就提前停止。

实际跑出来：草稿 6 分 -> 修订 -> 9 分 -> 停止。
Trace 里能看到两次 `reflection` 和一次 `revision`，这就是"质量成本"的直接证据。

## 4. 三范式对比：数字背后的判断

同一道"北京一日游"任务、同一套工具、同一个框架，Mock 模式实际运行：

| 范式 | LLM 调用 | 工具调用 | 步数 | 总 Tokens | 适合场景 |
|---|---:|---:|---:|---:|---|
| ReAct | 3 | 2 | 3 | 1666 | 路径不确定，需要边查边改 |
| Plan-and-Solve | 7 | 2 | 3 | 2753 | 步骤清晰，需要审核计划 |
| Reflection | 6 | 2 | 5 | 2720 | 质量敏感，能接受额外成本 |

三个观察：

1. **Plan 不一定比 ReAct 便宜**。本任务里 Plan 需要"规划 + 每步执行 + 综合"，调用次数反而最多。
   教材说 Plan 适合"逻辑链条清晰"的任务，但"清晰"不等于"便宜"。
2. **Reflection 的收益来自具体反馈**。第一次评审指出"没有分项、建议不具体"，修订后才把 91 元拆成 15 + 76。
   如果评审只说"再改改"，Reflection 就会空转。
3. **步数不等于调用数**。Plan 的 `steps=3` 是计划步骤数，LLM 调用是 7；报告必须同时列这两个指标，否则会误读。

完整报告：`reports/paradigm_comparison_mock.md`。

## 5. 遇到的问题与解决方法

### 问题 1：模型不按 ReAct 格式输出

**现象**：真实模型经常输出"我觉得应该先查天气"或 Markdown 围栏，没有 `Action:`。
**解决**：
- 解析器支持中英文冒号、代码围栏、JSON/单参数裸值；
- 第一次解析失败 -> 把错误输出和"格式修复提示"写回上下文，给一次自我纠正；
- 第二次仍失败 -> `parse_error`，Trace 保留原始输出，不伪造答案。

### 问题 2：工具参数类型不转换

**现象**：`from __future__ import annotations` 下，`int` 注解被当成字符串，`"41"` 直接传进函数。
**解决**：`typing.get_type_hints()` 解析注解；`ToolSpec.validate()` 做受控类型转换；未知参数报错。

### 问题 3：上下文越跑越长

**现象**：ReAct 每步都把完整历史塞进 prompt，几轮后 token 暴涨。
**解决**：`WindowMemory` + `ContextBuilder` 预算裁剪；保留系统提示和最后一条消息；`context` 事件记录丢弃数量。

### 问题 4：重试导致流式输出重复

**现象**：流式响应已经吐了一半，网络错误后重试，用户看到重复文本。
**解决**：`RetryingChatModel.stream()` 记录 `yielded`；一旦已输出，不再重放，直接抛错。

### 问题 5：Reflection 停不下来

**现象**：评审永远能挑出问题，循环无限改稿。
**解决**：`quality_threshold` + `reflect_rounds` 双刹车；评审要求输出 1–10 分与具体 issue。

### 问题 6：工作流变量类型丢失

**现象**：`${inputs.count}` 被替换成字符串 `"3"`，计算工具拿到 `"3"` 而不是 `3`。
**解决**：模板整串匹配时保留原类型；只有嵌入字符串才 `str()`；`condition` 单独做布尔求值。

## 6. 学习收获与反思

### 6.1 从"调通"到"可解释"

前几周的标准是"能跑出答案"。本周的标准变成了：

- 这个答案用了哪些工具、参数是什么？
- 模型当时看到了哪些消息？上下文丢了多少？
- 失败是模型格式问题、工具问题，还是配置问题？
- 换一个范式，成本差多少？

Trace 让这些问题有了可回答的抓手。**可观测性不是附加功能，而是框架的一等公民。**

### 6.2 框架的价值是"约束"

以前写 Agent，每个脚本都有自己的 `while` 循环、自己的 `try/except`、自己的日志格式。
框架化之后，范式被约束成 `_execute()`，工具被约束成 `ToolSpec`，模型被约束成 `ChatModel`。
约束带来两个好处：

- 新增能力有固定位置，不会到处散落；
- 对比和测试有统一口径，数字可信。

### 6.3 哪些地方还可以更好

- **原生 function calling**：目前是文本协议，下一步可以加 `FunctionCallAgent`，复用已有 `to_openai_schema()`；
- **异步与并发**：同步实现便于教学，但 Web 高并发需要外层线程池或 async 版本；
- **RAG / MCP / 多 Agent**：第 8–10 章再扩展，当前只留接口，不提前抽象；
- **可视化**：YAML 已经是"低代码"，但还缺一个画布前端；旧 `webapp` 可以作为可视化入口继续演进；
- **真实模型评测**：Mock 只验证链路，下一步用同一任务跑 3 个真实模型，记录格式失败率与成本。

### 6.4 一句话总结

**第 7 章让我从"会调用 Agent 的人"变成"知道 Agent 为什么能工作的人"。**
框架不是目的，它只是把前六章的知识变成可验证、可修改、可扩展的工程实体。
